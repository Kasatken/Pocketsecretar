# Пространства (collaboration) и «Ход дня»

Документ описывает **механики совместных пространств**, **предложений задач**, интеграцию с **календарём** и виджет **«Ход дня»** на экране «Сегодня»: данные в БД, HTTP API, поведение фронтенда и точки расширения.

См. также: [api.md](./api.md) (таблица маршрутов), [database.md](./database.md) (миграции), [frontend.md](./frontend.md) (маршрутизация).

---

## 1. Пространства — назначение

**Пространство** — изолированная «комната» для совместной работы: участники видят друг друга, **координатор** выдаёт приглашения, участники создают **предложения задач** с указанием **исполнителя**; исполнитель **принимает** или **отклоняет** предложение. После принятия, при указанных интервалах времени и подключённом Google Calendar, в календарь исполнителя может быть создано событие.

Пространство **не заменяет** общий доступ к календарю других людей: в календарь попадает только то, что согласовано через предложение и принято исполнителем (плюс логика слияния с событиями Google — см. ниже).

## 2. Модель данных (PostgreSQL)

Миграция: `backend/migrations/011_collab_spaces.sql`.

| Таблица | Назначение |
|---------|------------|
| `spaces` | Имя, тип, политика, создатель, метки времени. |
| `space_members` | Участник пространства: роль и уровень «шаринга». Составной ключ `(space_id, user_id)`. |
| `space_invites` | Одноразовый токен приглашения, срок действия, опциональная привязка к email, роль и `share_access` для вступившего. |
| `task_proposals` | Черновик/предложение задачи: автор, исполнитель, текст, опциональный интервал, статус, примечание исполнителя, `google_event_id`. |

### 2.1. Поля `spaces`

- **`space_type`**: `work` | `personal` | `custom` — классификация для UI (создание с экрана «Пространства» задаёт один из типов).
- **`policy`**: `proposals_only` | `direct_ok` — хранится в БД и отображается в UI как подсказка («задачи только через предложения»). **Сервер не ветвит** отдельные API для «прямых» задач: фактически весь согласованный поток идёт через `task_proposals`.

### 2.2. Роли `space_members.role`

| Значение | Смысл |
|----------|--------|
| `coordinator` | Создатель пространства получает роль при `CreateSpace`. Только координатор может создавать **приглашения** (`POST …/invites`). |
| `member` | Обычный участник: может создавать предложения (если не ограничен только наблюдением по смыслу продукта). |
| `observer` | **Не может** создавать предложения — API возвращает **403**. |

### 2.3. `share_access`

Значения: `full` | `partial` | `view_only` — задаются при **создании приглашения** и сохраняются у участника. В интерфейсе страницы пространства отображаются как «полный / частичный / просмотр». Логика ограничения по `share_access` на бэкенде для отдельных полей может наращиваться; сейчас ключевое ограничение — **роль observer** и проверки членства при операциях.

### 2.4. Статусы `task_proposals.status`

- **`pending`** — ожидает ответа исполнителя.
- **`accepted`** / **`declined`** — финальные ответы исполнителя.
- **`superseded`** — допустимо схемой БД, в текущем коде обработчиков не используется (зарезервировано).

## 3. HTTP API (пространства и предложения)

Все маршруты под **`/api/spaces`** с **`Authorization: Bearer`**. Регистрация в `backend/main.go`; обработчик — `backend/handlers/collab_spaces.go`, репозиторий — `backend/repository/collab_spaces.go`.

**Порядок маршрутов важен:** более специфичные пути (`calendar-overlays`, `pending-for-me`) зарегистрированы **до** `GET /api/spaces/{id}`, чтобы сегменты не перехватывались как `id`.

| Метод | Путь | Кто | Описание |
|-------|------|-----|----------|
| GET | `/api/spaces` | Участник | Список пространств пользователя с полями `my_role`, `my_share`. |
| POST | `/api/spaces` | Любой авторизованный | Создание: `name`, опционально `space_type` (по умолчанию `custom` в коде при пустом — см. обработчик), `policy` (по умолчанию `proposals_only`). Создатель вносится как **coordinator** с **full**. |
| GET | `/api/spaces/{id}` | Участник | Карточка пространства + `my_role` / `my_share`. Иначе **404**. |
| GET | `/api/spaces/{id}/members` | Участник | Список участников с email, ролью и `share_access`. |
| POST | `/api/spaces/{id}/invites` | **Только coordinator** | Тело: `invited_email` (опционально), `role`, `share_access`, `expires_days` (1…30, по умолчанию 7). Ответ: `token`, `expires_at`. |
| POST | `/api/spaces/join` | Любой авторизованный | Тело: `{ "token": "…" }`. Проверка срока, опционально **совпадение email** с `invited_email` приглашения. Успех: участник добавлен, приглашение **удалено** (одноразовость). |
| GET | `/api/spaces/{id}/proposals` | Участник | Все предложения в пространстве (в т.ч. история). |
| POST | `/api/spaces/{id}/proposals` | Не observer | Создание: `assignee_id` (обязателен, должен быть **участником** пространства), `title` (до 500 символов), `description` (до 8000), `proposed_start` / `proposed_end` в **RFC3339** — **оба сразу или оба пустые**. |
| POST | `/api/spaces/{id}/proposals/{proposalId}/respond` | **Только assignee** | Тело: `status`: `accepted` \| `declined`, `assignee_note`. Только пока `pending`. |

### 3.1. Календарь: оверлеи принятых предложений

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/api/spaces/calendar-overlays` | Query: **`time_min`**, **`time_max`** (RFC3339, UTC на wire). Возвращает принятые предложения текущего пользователя как **исполнителя**, у которых задан интервал и он пересекается с диапазоном. Используется для слияния с событиями Google на «Сегодня» и «Календарь». |

### 3.2. Ожидающие ответа предложения (уведомления в приложении)

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/api/spaces/pending-for-me` | Агрегация по пространствам: где текущий пользователь — **исполнитель** и статус **`pending`**, только если он состоит в пространстве (`space_members`). Ответ: `total`, `spaces[]` с `space_id`, `space_name`, `pending_count`, `latest_title`, `latest_created`. |

### 3.3. Принятие предложения и Google Calendar

В `RespondProposal` при **`accepted`** и наличии **`proposed_start`** / **`proposed_end`**:

1. Проверяется конфигурация Google OAuth на сервере.
2. По **пользователю-исполнителю** берётся refresh-токен Google.
3. Создаётся событие в его календаре (см. `createGoogleCalendarInstantRangeEvent` в обработчиках календаря); в **extendedProperties** может сохраняться идентификатор предложения для сопоставления.
4. В ответ добавляются `google_event_id` либо **`calendar_warning`** (нет календаря, ошибка API и т.д.).
5. В БД обновляется `google_event_id` у предложения при успехе.

Исполнитель без связанного Google всё равно может **принять** предложение — оно сохранится как accepted, предупреждение уйдёт в UI.

## 4. Фронтенд: экраны и механики

### 4.1. Маршруты

- `/spaces` — список, создание, вступление по ссылке/токену (`frontend/src/pages/SpacesPage.tsx`).
- `/spaces/:id` — карточка пространства (`SpacePage.tsx`).
- Ссылка-приглашение: базовый URL приложения + **`/spaces?token=…`** (токен парсится утилитой `extractInviteToken`).

Создание пространства с UI передаёт **`name`** и **`space_type`**; **`policy`** на бэкенде по умолчанию `proposals_only` (поле в форме создания не выставляется — только API).

### 4.2. Страница пространства

- Отображаются роль и уровень доступа текущего пользователя; для `proposals_only` показывается пояснение.
- **Участники** — список из `GET …/members`.
- **Приглашение** — только у **coordinator**: роль и share для будущего участника, срок, опциональный email; после создания показываются токен и готовая ссылка.
- **Предложить задачу** — сворачиваемый блок; доступен, если роль не `observer`. Форма: исполнитель из списка участников, заголовок, описание, пара полей даты/времени (локальный ввод → ISO при отправке).
- **Предложения** — **история**: сворачиваемый блок («Свернуть» / «Развернуть»), в свёрнутом виде краткая сводка (число записей и сколько в ожидании / принято / отклонено). Якорь **`#proposals`** разворачивает блок и прокручивает к секции `id="space-proposals"`.
- **Ответ исполнителя**: для строк со статусом `pending` и `assignee_id === текущий пользователь` — комментарий, «Принять» / «Отклонить».

После успешного ответа на предложение вызывается **`notifyPendingProposalsChanged()`** (`frontend/src/lib/pendingProposalsEvents.ts`) — шапка приложения **сразу** перезапрашивает `pending-for-me` (без ожидания интервала опроса).

### 4.3. Уведомления о pending-предложениях (`AppLayout`)

- Периодический запрос **`GET /api/spaces/pending-for-me`**: при монтировании, каждые **90 с**, при возврате на вкладку (`visibilitychange`), при событии **`pocketsecret:pending-proposals-changed`**.
- **Бейдж** на пункте навигации «Пространства» — число ожидающих ответа.
- **Полоска** под шапкой: текст, ссылка «Открыть предложения» на первое пространство из ответа (самое свежее по серверной сортировке) с **`#proposals`**, кнопка «Скрыть» скрывает полоску для текущего «снимка» данных; при появлении **новых** ожидающих (другая сигнатура) полоска снова может показаться.

### 4.4. «Сегодня» и «Календарь»: слияние с Google

Файлы: `frontend/src/lib/mergeAcceptedSpaceProposals.ts`, `frontend/src/lib/spacesApi.ts` (`fetchAcceptedCalendarOverlays`), страницы **`AppPage.tsx`** и **`CalendarPage.tsx`**.

Алгоритм **`mergeAcceptedSpaceProposalsIntoEvents`**:

1. Сопоставление по **`space_proposal_id`** из метаданных события Google (если есть) с оверлеем.
2. Сопоставление по **`google_event_id`** предложения с id события (с учётом вариантов суффикса `@google.com`).
3. **Эвристика** для старых событий: то же название (нормализованное) и близкое начало/конец (допуск по времени).
4. **«Призрачные» слоты**: если оверлей не привязался ни к одному событию, в список добавляется синтетическое событие с id вида `space-proposal-{id}` — чтобы слот отображался даже без записи в Google. Утилита **`isSpaceProposalGhostEvent`** отличает такие элементы.

У принятых предложений в списке задач и в блоке «следующее событие» может показываться **`SpaceProposalCalendarBadge`** (автор, аватар, название пространства).

## 5. «Ход дня» (экран «Сегодня»)

Реализация: `frontend/src/pages/AppPage.tsx` + стили `AppPage.module.css`, палитра неба — **`frontend/src/lib/dayGaugeSkyGradient.ts`**.

### 5.1. Смысл виджета

- **12 сегментов** — условные «доли» локальных **календарных суток** от полуночи до полуночи (`startOfLocalDay` / `endOfLocalDay`).
- Число **закрашенных** сегментов:  
  `floor((доля прошедшего дня) * 12)`, но не меньше **1**, если день уже начался и доля меньше одной двенадцатой (чтобы ночью полоса не была полностью пустой). Верхняя граница — 12.
- Подпись для доступности: «День прошёл примерно на N из 12 долей».

### 5.2. Цвет заполненных сегментов («небо»)

Все **включённые** сегменты используют **один** вертикальный градиент `linear-gradient(180deg, start, end)`, где `start`/`end` берутся из таблицы **`SKY_STOPS`** по **локальному** часу (с дробной частью минут/секунд). Интерполяция между соседними опорами — **RGB lerp** между заданными hex-цветами; в узких интервалах между сильно разными оттенками возможна визуальная «грязь», поэтому критические зоны (например поздний день перед закатом) разбиты дополнительными опорами.

### 5.3. Отладка времени суток для шкалы

- URL: **`?skyHour=17.5`** (дробный час допускается).
- Или **`sessionStorage.setItem('skyHour', '17.5'); location.reload()`**; сброс: `removeItem('skyHour')`.

Функция **`getEffectiveSkyHour`** возвращает либо отладочное значение, либо реальное локальное время.

### 5.4. Обновление во времени

- **`nowTick`** — каждые **30 с** (доля дня, журнал событий, фаза суток в тексте).
- **`skyTick`** — каждые **60 с** (пересчёт градиента неба для шкалы).

### 5.5. Тег фазы суток («Утро / День / Вечер / Ночь»)

Функция **`dayPhaseRu`** в `AppPage.tsx` **независима** от таблицы `SKY_STOPS`:

- Утро: 5:00–12:00  
- День: 12:00–17:00  
- Вечер: 17:00–22:00  
- Ночь: остальное  

Это **только подпись** рядом со счётчиком событий; цвет сегментов «Ход дня» идёт из **`previewSkyGradientAtHour(getEffectiveSkyHour(…))`**, поэтому граница «Вечер» в 17:00 и переход градиента к закату могут визуально не совпадать дословно — это ожидаемо.

## 7. Идеи для развития (не реализовано)

- Серверная проверка **`policy`** (например запрет предложений при `direct_ok` с другой моделью задач).
- Использование статуса **`superseded`**.
- Редактирование ролей участников после вступления, отзыв приглашений без входа по токену.
- Web Push / email при новом предложении (сейчас только in-app опрос и событие после ответа).
