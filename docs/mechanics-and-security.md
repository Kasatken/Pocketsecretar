# Механики продукта и безопасность

Документ для онбординга: как устроены игровые и продуктовые механики на сервере и в браузере, и какие решения по безопасности уже заложены в коде — без этого легко ошибиться при доработках или деплое.

---

## Часть 1. Механики

### Опыт и уровень

- За **первое** успешное завершение **конкретного** события Google Calendar (отметка «выполнено») пользователь получает **+25** очков опыта (`xpPerCalendarEventComplete` в `handlers/calendar_events.go`).
- Повторная отметка того же `google_event_id` не даёт XP: запись в `calendar_event_completions` уникальна по `(user_id, google_event_id)`.
- **Уровень** пересчитывается в БД при начислении:  
  `level = (experience_points + начисление) / 100 + 1`  
  (см. `repository/users.go`, `AddExperienceInTx`). То есть каждые **100** XP после последнего порога поднимают уровень на 1 (начальный уровень в данных миграций — 1).

Итог: прогресс привязан к реальным событиям календаря и от серверной проверки существования события в Google.

### План Free / Pro

- В таблице `users` поле `plan`: **`free`** или **`pro`** (ограничение CHECK в миграции).
- **Умные задачи** (smart-task): для **free** действует **дневной лимит** запусков; счётчик ведётся в **`user_daily_smart_tasks`** по календарному **дню в UTC** (`repository/smart_tasks.go`). Лимит задаётся `FREE_SMART_TASK_LIMIT`, значение «сброса» для UI отдаётся как `smart_tasks_today.resets_at` — **полночь UTC** (`QuotaResetsAtUTC`).
- Для **pro** лимит smart-task по этой таблице не применяется в том же виде (логика «без дневного ограничения» завязана на `isProPlan` в обработчиках и ответах `/api/auth/me`).
- Активация Pro через промокод — см. раздел «Промокод» ниже и `handlers/profile.go` (`RedeemPromo`).

Важно для UX: пользователь в Москве может видеть «обнуление» лимита в локальное время, отличное от полуночи по календарю — потому что день квоты **UTC**.

### Умные задачи (smart-task)

**Назначение:** пользователь вводит текст на естественном языке; сервер запрашивает LLM (OpenRouter), парсит **строгий JSON** с задачами, нормализует поля и создаёт события в **Google Calendar** от имени пользователя.

**Нюансы:**

1. **Долгий запрос:** обработка может идти долго (LLM + Google). Сервер может ответить **HTTP 202** с `job_id`; клиент поллит `GET /api/calendar/smart-task?job=…` (см. `frontend/src/lib/calendarApi.ts`). Результаты job хранятся **в памяти процесса** и удаляются примерно через **15 минут** после завершения (`smart_task_jobs.go`).
2. **Привязка job к пользователю:** опрос статуса допускается только если `job` принадлежит тому же `user_id`, что и Bearer-токен (`getForUser`).
3. **Квота:** перед выполнением для free проверяется/атомарно увеличивается счётчик (`TryIncrementCapped`), чтобы не превысить лимит при параллельных запросах.
4. **Парсинг ИИ:** при ошибке парсинга JSON возможна вторая попытка «починки» ответа через отдельный системный промпт (`smart_task.go`).
5. Ограничение количества перерывов в день и прочие правила нормализации задаются в коде обработчика (например `capBreakTasksPerDay`).

### Ежедневный совет (daily advice)

- Строится по событиям Google Calendar за окно от **начала текущего календарного дня** до **конца дня через 6 дней** — константа `dailyAdviceHorizonDays`, часовой пояс для понятия «сегодня» и границ дня — **`Europe/Moscow`** (`handlers/daily_advice.go`).
- **Кэш** в таблице `user_daily_advice`: ключ `(user_id, day)` где `day` — строка даты в Москве; хранится текст совета и **`events_sig`** — сигнатура набора событий + отпечаток персонализации пользователя (bio, personalization_note, chronotype). Если календарь или профиль изменились, при том же дне совет пересчитывается.
- Параметр **`refresh=1`** на GET заставляет перестроить совет (если позволяют ключ API и Google).
- При недоступности генерации возможен ответ с пометкой «устаревший» совет (`stale`) — см. обработчик для точных условий.
- На главной странице приложение периодически опрашивает совет (**интервал порядка нескольких минут**), чтобы подтянуть совет, когда события «догрузились» или изменились (`AppPage.tsx`, константа опроса).

### Помидоро (Pомодоро)

- Реализовано **только на клиенте** (`hooks/usePomodoro.ts`): фазы **25 мин работа**, **5 мин короткий перерыв**, **15 мин длинный** после каждого **четвёртого** завершённого блока работы.
- Состояние **не синхронизируется** с сервером и **не влияет** на XP — это таймер для фокуса в UI.

### Бэклог идей

- Локальные «стикеры» в БД (`user_backlog_idea`): текст, цвет из фиксированного набора, тег с ограничением символов.
- **Запланировать** (`POST …/schedule`) создаёт событие в Google Calendar на выбранную дату (опционально время) **без LLM** — обычный HTTP к Calendar API с токеном пользователя.

### Интерфейс «Сегодня» (главная)

- Загружает события за локальный день и связанные действия (удаление, завершение с начислением XP).
- Визуальные метафоры (фаза дня, градиент «неба», шкала уровня) основаны на локальном времени браузера и данных пользователя из `/api/auth/me`.

## Часть 2. Безопасность

### Аутентификация и токены

| Механизм | Реализация |
|----------|------------|
| Пароли | Хеш **bcrypt** (`security/password.go`), пароли в открытом виде в БД не хранятся. |
| Access token | **JWT** (HS256), короткий TTL (`ACCESS_TTL_MIN`), передаётся в **`Authorization: Bearer`**, хранится на клиенте в **памяти** React-состояния — не в localStorage. |
| Refresh token | Отдельный JWT, подписан **другим** секретом; выставляется в cookie **`refresh_token`**: **HttpOnly**, **SameSite=Lax**, флаг **Secure** включается через **`COOKIE_SECURE`** для продакшена. |
| Проверка на API | `middleware.RequireAuth` валидирует Bearer только через **`ParseAccessToken`** (секрет access). Refresh-токен с заголовком Bearer **не примет** — другая подпись. |

Рекомендация для усиления (в коде сейчас не обязательно сделано): явно проверять в middleware поле **`sub`/subject** JWT на значение `access`, чтобы исключить теоретическую путаницу типов токенов при будущих изменениях.

### OAuth Google

- Параметр **`state`** в redirect — это короткоживущий JWT с subject **`google_oauth_state`**, проверяется через **`ParseGoogleOAuthState`** (`security/tokens.go`).
- При старте OAuth пользователь идентифицируется по **cookie refresh** (сессия уже должна существовать).

### CORS

- Разрешён **ровно один** origin из **`CORS_ALLOWED_ORIGIN`**, выставляются **`Access-Control-Allow-Credentials: true`** для cookie-сессий (`middleware/cors.go`).
- В продакшене origin фронтенда и значение переменной должны совпадать **буквально** (схема, хост, порт).

### Ограничение частоты запросов

- Регистрация и вход: **12** запросов с одного IP за **минуту** (скользящее окно в памяти; для IP учитывается **`X-Forwarded-For`**, если есть — первый адрес в списке) — см. `handlers/auth.go`, `clientIP`.
- Промокод: отдельный лимит (**10**/мин) на IP (`promoLimiter`).
- Встроенный `RateLimiter` в `middleware/ratelimit.go` использует другой расчёт IP **без** `X-Forwarded-For` — если за прокси включите только middleware-лимит, учитывайте это при интерпретации логов.

### Загрузка аватаров

- Ограничение размера тела и файла (`MaxBytesReader`, `AvatarMaxBytes`).
- Тип файла определяется по **содержимому** (`http.DetectContentType`), допускаются только типы, для которых есть расширение (JPEG/PNG/WebP) — см. `handlers/profile.go`.
- Имя файла: **`userID_случайныебайты.расширение`**, без пользовательского имени — снижает риск path traversal.
- Удаление старого файла допускается только если URL старого аватара начинается с префикса публичного пути **и** имя файла содержит **тот же** `user_id` в префиксе — защита от ссылки на чужой путь.

### Секреты и ключи API

- **`OPENROUTER_API_KEY`**, секреты JWT, **`PRO_PROMO_CODE`**, Google client secret — только на **сервере**; фронт их не получает.
- Запросы к OpenRouter идут с сервера (`handlers/openrouter.go`); опционально **`OPENROUTER_PROXY`** для исходящего трафика.

### Данные и доступ к БД

- Запросы к PostgreSQL через **параметризованные** запросы (`$1`, `$2`, …), что снимает классический **SQL injection** при сохранении текущего стиля кода.
- Идентификатор пользователя для операций берётся из **контекста**, установленного после проверки JWT, а не из тела запроса — клиент не может подставить чужой `user_id` в защищённых эндпоинтах.

### Smart-task jobs в памяти

- **Риск:** при рестарте сервера активные job теряются; **риск безопасности:** при компрометации памяти или отладочном доступе job видны только по ID — опрос привязан к **user_id** (см. выше).
- Для публичного продакшена при высокой нагрузке имеет смысл вынести очередь в Redis и хранить там же привязку user→job.

### Промокод Pro

- Код на сервере один: сравнение **константы** `PRO_PROMO_CODE` с телом запроса; без кода в конфиге эндпоинт отвечает, что активация не настроена.
- Перебор затрудняется rate limit по IP.

### Клиентский фронт (XSS и данные)

- React по умолчанию экранирует текст при выводе; пользовательский контент (bio, советы) отображается как текст, не как `dangerouslySetInnerHTML` — при сохранении текущих практик **XSS через сохранённый профиль** маловероятен.
- Любые новые места с «сырым» HTML потребуют отдельной санитизации.

### CSRF и cookie refresh

- Изменение состояния от имени залогиненного пользователя через API обычно идёт с **Bearer** из памяти; cookie refresh используется для **`POST /api/auth/refresh`**.
- **SameSite=Lax** снижает риск отправки cookie сторонним сайтом в части сценариев; для максимальной строгости на отдельном домене API иногда добавляют CSRF-токены или заголовок — сейчас в проекте этого нет, модель рассчитана на same-site или осторожную настройку CORS.
